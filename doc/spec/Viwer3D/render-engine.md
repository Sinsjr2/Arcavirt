# 描画エンジン

本書は、宣言ツリーを実際の描画へ橋渡しする部分から、内部の描画方式、見え方、マテリアルと色、
カメラの描画計算と操作、アセットのキャッシュ、画像キャプチャ、設定のライフサイクルまでを
定める。これらはレンダーループ実装時に一括で触る範囲である。描画基盤・座標規約の前提は
[index.md](index.md) と [project-foundation.md](project-foundation.md) にある。

## 宣言ツリーと描画

毎フレーム生成される使い捨ての宣言ツリーを、複雑な差分比較（diffing）を一切行わず、上から順に
単純走査（トラバース）して、NeoVeldrid の描画コマンドの配列をただ再構築する。

Web の React では古いツリーと新しいツリーを細かく比較し、変わった部分だけを反映する重い計算を
行う。しかし 3D グラフィックス（Vulkan / NeoVeldrid）では、毎フレーム画面全体をクリアして
1 から描き直すのが基本である。CPU 側で「何が変わったか」を細かく比較・追跡するコストよりも、
単純な構造体（位置や回転の行列データ）を上から順に読み取って GPU のバッファに一斉に書き込む
方が、C# のメモリの連続性を活かせて圧倒的に高速である。ツリーのノード数が数千〜数万程度で
あれば、差分を計算する方がかえって遅くなる。

描画エンジンは、形式に依存しない境界インターフェース `IDrawableSource` だけに依存する。本書を
その正典とする。`IDrawableSource` は、名前つきノードの階層・メッシュ・材質を、上書き
（NodeOverride / ColorOverride）を受けて最終的な描画物として返す契約である。描画エンジンは
glTF や SharpGLTF を知らない。glTF 読み込みはこの契約の 1 実装で、内部で SharpGLTF を使う
（[project-foundation.md の形式に依存しない境界](project-foundation.md#形式に依存しない境界)）。
新種ノードもこの契約を実装する形で追加でき、描画エンジン本体・中核ノードを変更せずに拡張
できる（[scene-nodes.md の拡張の方針](scene-nodes.md#拡張の方針)）。

接続の流れは「宣言ツリー → 単純走査 → `IDrawableSource` → NeoVeldrid の描画命令」である。
他の宣言的ライブラリでは、react-three-fiber は reconciler が JSX を Three.js オブジェクトへ
対応づけ、elm-3d-scene は view が生成したシーン値をエンジンが描き、Qt Quick 3D はフロント
エンドの記述をバックエンドのシーングラフへ反映し RHI が描く。本ライブラリは差分なしの単純
走査でこれを行う。

## 内部描画と実行環境

glTF 内のパーツ（ノード／メッシュプリミティブ）ごとに個別に描画命令（DrawCall）を発行し、
その直前に定数バッファ（行列と色情報）を更新する。ゲームのようにボーン（スキニング）を使った
一括描画にすると 3D 数学が難解になりバグの温床になる。今回は対象が 1〜数台の機械でパーツ数も
数百個程度のため、個別 DrawCall でも現代の GPU（NeoVeldrid / Vulkan）なら余裕で動作する。

完全なシングルスレッドで設計する。C# の `async/await` も単一スレッド上で協調的に動作させる
（シングルスレッド・マルチタスク）。シングルスレッドに絞る理由は性能や安全のための単純性で
ある。スレッド間のロックや、状態の複製（スナップショット）の手間・バグを根本から排除し、
最短ルートで実装・保守できる。なお NeoVeldrid 自体は多くのオブジェクトを複数スレッドから
利用できるが、本ライブラリはその機能に依存せず、単純性を優先してシングルスレッドを採る。

時間の進め方は `ITimeSource` を経由し、実時間（可変）とシミュレーション用（固定ステップの
コマ送り）の双方に対応する。`ITimeSource` の定義と 2 実装の正典は
[project-foundation.md の技術選定](project-foundation.md#技術選定) にある。本書ではループでの
使用箇所として、デルタタイムをアプリの状態更新に渡す形を用いる
（[scene-nodes.md の評価と更新のタイミング](scene-nodes.md#評価と更新のタイミング)）。

## 描画の見え方

本ライブラリの目的は機械パーツの観察・検査であり、写実性ではなく視認性を最優先する。いずれの
規則も、追加のネイティブ依存を持たない純 C# で、無彩色を基本としてパーツの色味を歪めないよう
構成する。

ライティングは、カメラに追従する単一の指向性ライト（ヘッドライト）＋わずかな環境光とし、
落とし影は描かない。ヘッドライトは視線軸から少しだけ（上・横へ 20〜30 度程度）ずらしたカメラ
相対の固定位置に置く。これにより、どの角度から見てもパーツが暗く潰れず、形状の凹凸が読み
やすい。真上からの均一な環境光だけにすると陰影が消えて形状が平坦に見え、目的に反するため
採らない。落とし影（シャドウマップ）は別レンダーパスを増やし、単純走査・個別描画命令の単純さを
壊すうえ検査用途に不要なので実装しない。なお面の向きによる明暗のグラデーション（陰影）は別パス
不要で、シェーダ内の 1 ドット積で得られる。光源の方向・色・強さは API に露出せず固定し、状態は
カメラから導出する。

面の表裏は、glTF の各マテリアルの両面指定（doubleSided）に従い、ライブラリで一律に上書きしない
（渡されたモデルをそのまま描く方針）。単面指定の面は裏面をカリングし、両面指定の面は両面描画
する。両面の裏側を描くとき、その面の法線はカメラと逆を向くため、フラグメントシェーダで裏面の
ときだけ法線を反転して正しく照らす。これはモデルを上書きしているのではなく「モデルのまま正しく
見せる」ためのもので、単面マテリアルの裏面はそもそも描かれないので発動しない。フロントフェースの
ワインディングは glTF 規格の反時計回り（CCW）に合わせる。

半透明（glTF の alphaMode）は、不透明（OPAQUE）・くり抜き（MASK）を完全対応し、半透明（BLEND）も
尊重するが、並べ替えは半透明だけに限定する。毎フレームの走査で描画命令を「不透明」と「半透明」に
振り分け、まず不透明をツリー順そのまま描き（深度テスト＋書き込みオン）、そのあと半透明だけを
カメラからの距離で奥→手前に並べ替えて描く（深度は読むが書かない）。これにより、毎フレーム全体を
並べ替えない方針を保ちつつ半透明を尊重する。既知の妥協として、このパーツ単位の並べ替えは完全
ではなく、半透明物どうしが複雑に重なる場合などはまれに混ざり方が崩れる。これは全リアルタイム 3D
が受け入れる標準的妥協で、カバーや窓が数枚程度の機械パーツでは実用上問題にならない。完全解
（順序非依存の手法）は重く、現時点では過剰として採らない。

奥行きは、ニア／ファー面をライブラリが毎フレーム自動で決める（非公開）。読み込んだモデルの
大きさ（バウンディング）とオービットカメラの距離から、見ている対象をぴったり挟むように毎
フレーム計算する。範囲をきつく挟むほど深度精度に余裕が出るため、これが Z ファイティング
（接した面のチラつき）対策の本命である。ズームで近づけば範囲も自動的に狭まる。深度バッファは
標準的な設定をそのまま使う（不透明は深度テスト＋書き込みオン、半透明は読むが書かない）。
より強力な「リバースド Z」は設定の手間が増え本用途では過剰なので採らないが、遠くでチラつきが
出たときに追加する余地は残す。ぴったり同じ位置にある面（面一に作ってある等）のチラつきは
精度では直せず、モデルの作りの性質であるためライブラリは勝手にずらさない。

輪郭のなめらかさは MSAA（マルチサンプル）を使い、既定 4x とする。ポリゴンの輪郭（ギアの歯や
ローラーの曲面など）のギザギザを滑らかにする。デバイスが非対応なら、能力を問い合わせてから
対応する最大値へ自動で落とす。サンプル数だけは設定可能にする（リアルタイム表示は 4x、ヘッド
レスの大量バッチは速度優先で 1x、という現実の使い分けがあるため）。これは作成時に決める設定
（[Tier1](#描画パラメータの設定ライフサイクル)）である。MSAA の絵はそのままでは保存できない
ため、ライブラリが自動で一度ふつうの 1 枚の画像に解像（resolve）してから、画面表示にも
ヘッドレスの PNG 取り出しにも回す（[画像キャプチャ機構](#画像キャプチャ機構)）。深度バッファも
MSAA に合わせて複数サンプルで作る。MSAA が滑らかにするのはポリゴンの輪郭のみで、テクスチャ内の
模様やくり抜き（MASK）のふちは滑らかにならないが、単色寄りの機械パーツが主役なので実用上
十分である。くり抜きのふちまで滑らかにする小技（アルファ・トゥ・カバレッジ）は必要時に後で
足す。

背景は中間グレーを既定とし、RGBA（透明も可）で変更できる。無彩色の中間グレーはパーツの色味を
歪めず、明部も暗部も見やすく目が疲れにくい。背景色は毎フレーム自由に変えられる
（[Tier2](#描画パラメータの設定ライフサイクル)）。ヘッドレスで透明背景の PNG を出して後から
合成する需要に応えるため、透明にできるが、その前提として作成時にアルファ付きの色フォーマットを
選ぶ必要がある（[Tier1](#描画パラメータの設定ライフサイクル)）。画面表示ではアルファは無視され、
ヘッドレスの PNG ではアルファが保たれる。基準グリッド（床）はノードとして扱い、その仕様は
[scene-nodes.md の GridNode](scene-nodes.md#gridnode) にある。グリッドの線も MSAA で滑らかになる。

## マテリアルと色

glTF の PBR（metallic-roughness）は捨てずに簡略解釈する。baseColor とテクスチャを拡散反射の
基本色とし、metallic / roughness はスペキュラ（ハイライト）の強さ・鋭さへ線形に写像するだけに
留める（拡散は Lambert、スペキュラは Blinn-Phong）。これにより「金属はテカり、樹脂はマット」
程度の区別はつき、色上書きが正しく機能する。

色上書き（[scene-nodes.md の ColorOverride](scene-nodes.md#coloroverride) で宣言する）は、描画
状態（GPU のパイプライン）を切り替える重い処理を一切せず、トランスフォーム行列と一緒に色上書き
情報を定数バッファ（Uniform Buffer）で GPU へ送信する。ブレンドモードは、完全に単色で塗り
つぶす Replace と、元の質感（金属感やテクスチャ）を残したまま色を被せる Multiply（乗算）の
2 種類を、シェーダ側の動的分岐で処理する。シェーダ内の動的分岐は色上書きモードのみとする。
描画パフォーマンスへの影響は皆無である。

## カメラの描画計算と操作

採用するカメラは、注視点を中心に回るオービットカメラである。カメラの状態 `CameraState` は
注視点・距離・方位角・仰角・投影モード・平行投影時の視野幅で持つオービット・パラメータ表現で
あり、その型の正典は
[scene-nodes.md のカメラのシーンへの組み込み](scene-nodes.md#カメラのシーンへの組み込み) に
ある。

描画時には、方位角・仰角・距離から位置を球面→直交で一度だけ算出し、ビュー行列を生成する。
逆方向（位置から角度）の逆算は行わない。

```csharp
// 描画側：CameraState から位置を算出し、CreateLookAt へ
float ce = MathF.Cos(c.Elevation), se = MathF.Sin(c.Elevation);
float ca = MathF.Cos(c.Azimuth),   sa = MathF.Sin(c.Azimuth);
Vector3 offset = new(c.Distance * ce * sa, c.Distance * se, c.Distance * ce * ca);
Vector3 position = c.Target + offset;
Matrix4x4 view = Matrix4x4.CreateLookAt(position, c.Target, Vector3.UnitY);   // 上方向は世界 Y
```

投影は投影モードで分岐する。透視投影は視野角 45 度固定で、ニア／ファーは前述のとおり自動で
決める。平行投影は視野の幅（`OrthographicSize`）で画面に収める範囲を決め、ニア／ファーは同様に
自動である。

経緯として、CameraState を位置・注視点・上方向で持つ汎用表現も検討した。ビュー行列へ直接
流せる利点があるが、オービット操作のたびに位置から角度を逆算して位置を再構築する往復が必要で、
わずかな浮動小数誤差が蓄積し得るうえ、真上・真下付近で方位角の逆算が定まりにくい特異点を抱える。
本ライブラリは自由飛行を持たないオービット専用のため、その汎用性は不要と判断し、操作が単純で
堅牢になるパラメータ表現を採った。位置・注視点・上方向表現の利点（直接 `CreateLookAt` に渡せる）
は、パラメータ表現でも位置を一度算出してから渡すだけで失われない。

操作（CameraInteraction）は、マウス操作から新しい CameraState を算出する純粋関数群として
ライブラリが提供し、イベントハンドリングと状態保持はアプリケーション側が担当する。バグの
起きやすい 3D 数学計算をライブラリに隠蔽して負担を減らしつつ、その計算結果を実際にカメラへ
適用するかの決定権は 100% アプリ側に残す。操作モードのモーダルな切替は持たず、ジェスチャごとに
対応するメソッドを呼ぶ。

```csharp
// ライブラリが提供する純粋関数（状態を持たない）
public static class CameraInteraction {
    public static CameraState Orbit(CameraState camera, Vector2 mouseDelta);
    public static CameraState Pan(CameraState camera, Vector2 mouseDelta, float viewportHeight);
    public static CameraState Zoom(CameraState camera, float wheelDelta);   // ProjectionMode で内部分岐
}

// アプリ側のイベント処理（どの操作を呼ぶかはアプリが決める）
void OnMouseDrag(Vector2 delta, bool shiftHeld) {
    if (shiftHeld) {
        state.Camera = CameraInteraction.Pan(state.Camera, delta, state.ViewportHeight);
    } else {
        state.Camera = CameraInteraction.Orbit(state.Camera, delta);
    }
}

void OnMouseWheel(float wheelDelta) {
    state.Camera = CameraInteraction.Zoom(state.Camera, wheelDelta);
}
```

各操作の中身は次のとおり。Orbit は方位角・仰角に加算し、仰角を ±一定角（例: 89 度）でクランプ
して極点での反転を防ぐ。Zoom は透視なら距離を増減し、平行なら視野幅を伸縮する。Pan は方位角・
仰角から求めたカメラの右方向・上方向の平面内で注視点を平行移動し、移動量は距離や視野幅に応じて
拡縮して操作感を一定に保つ（ピクセルから世界量への換算にビューポート高さを使う）。

```csharp
public static CameraState Orbit(CameraState c, Vector2 mouseDelta) {
    c.Azimuth   += mouseDelta.X * OrbitSensitivity;
    c.Elevation -= mouseDelta.Y * OrbitSensitivity;
    c.Elevation = Math.Clamp(c.Elevation, -MaxElevation, MaxElevation);   // 極点での反転防止
    return c;
}

public static CameraState Zoom(CameraState c, float wheelDelta) {
    if (c.Projection == ProjectionMode.Perspective) {
        c.Distance = Math.Clamp(c.Distance * (1 - wheelDelta * ZoomSensitivity), MinDistance, MaxDistance);
    } else {
        c.OrthographicSize = Math.Clamp(c.OrthographicSize * (1 - wheelDelta * ZoomSensitivity), MinSize, MaxSize);
    }
    return c;
}
```

経緯として、Orbit / Pan / Zoom を持続的な操作モード（Orbit / Pan / Zoom を状態として保持し、
切替 UI で選ぶ方式）として持つ案を一度は採ったが、ボタンを置かない方針により不要になったため
廃止し、ジェスチャごとに対応するメソッドを呼ぶ直接操作へ一本化した。ドラッグ＝オービット、
ホイール＝ズーム、Shift＋ドラッグ＝パンである。

マウスのドラッグは、現時点では相対マウスモードを使わず、カーソルは常時表示とする。ドラッグ
操作は絶対モードのままカーソル位置の前フレーム差分を読んで処理し、アンカーへのワープは行わ
ない。この帰結として、カーソルが画面やウィンドウの端に達すると差分が頭打ちになり、連続的な
回転はカーソルが画面内で動ける範囲に制限される。これは現時点で許容する。経緯として、端で
頭打ちにならない連続回転が必要になった場合に備え、相対マウスモード（カーソルを隠して固定し、
無限の移動量を読む）へ切り替える拡張余地がある。その場合はカーソルが非表示・固定になることと、
読み取る量の符号が反転することが代償になる。マウス差分の供給は
[input-architecture.md](input-architecture.md) が担う。

## アセットのキャッシュとメモリ管理

毎フレーム宣言ツリーを使い捨てる設計では、重い glTF ファイルの読み込みによる画面フリーズや、
古いデータがメモリに残り続ける肥大化（VRAM のリーク）を防ぐ必要がある。これをライブラリ内部の
完全全自動キャッシュで解決し、開発者は `Load()` や `Dispose()` を一切書かない。

- ロードは非同期・プレースホルダー方式とする。ツリーに新しいパス（例: `"heavy.gltf"`）が登場し、
  キャッシュになければ即座に非同期ロードを開始する。非同期にすることでループを止めず、画面
  フリーズを防ぐ。キャッシュのキーはファイルパスで、そのパスを使う配置が 1 つでもある限り生存
  する。同じファイルを N 回置いても読み込み・GPU 転送は 1 回で、N 配置で共有する。
- 解放は Time-to-Live 付きの生存カウンターで行う。毎フレームのツリー解析時、各アセットの
  「最後にツリーに登場した時刻」を記録する。ツリーから消えた（画面遷移などで使われなくなった）
  アセットは、最後の登場から 10 秒（10000 ミリ秒）一度も使われなければ、安全に GPU（VRAM）と
  メインメモリから完全に自動解放（Dispose）する。10 秒の猶予により、ユーザーが一瞬だけタブを
  切り替えてすぐ戻るケースでの不必要な解放・再ロード（プチフリーズ）を防ぐ。

## 画像キャプチャ機構

ヘッドレスでの PNG 保存と生ピクセル提供（メディア出力のスコープは
[project-foundation.md のメディア出力のスコープ](project-foundation.md#メディア出力のスコープ)）を、
描画を止めずに行う。

MSAA を使う場合、その絵はそのままでは保存できないため、まず一度ふつうの 1 枚の画像に解像
（resolve）する。次に、画面のガクつきを防ぐため、描画完了直後に GPU 内部でステージング・
テクスチャへ超高速コピーし、`System.Threading.Channels`（非同期キュー）を介してバックグラウンドの
協調タスクでピクセルデータを引き抜く。引き抜いたピクセルは、生データのまま提供するか、純 C# で
PNG にエンコードして保存する。動画への保存は行わない。

## 描画パラメータの設定ライフサイクル

描画に必要なパラメータを「いつ・どのように設定／変更するか」を決めておく。判断の軸は 1 つ、
「そのパラメータを変えるのに GPU の資源（フレームバッファやパイプライン）を作り直す必要が
あるか」である。これで 2 階層に分ける。

Tier1（GPU 資源に焼き付くため、起動時の作成オプションとして一括で渡す。変更は作り直し）。

- グラフィックス API（主軸 Vulkan）／使う GPU
- 出力先の種類（画面ウィンドウ／ヘッドレスのオフスクリーン）
- 解像度（ウィンドウや出力テクスチャのサイズ）
- 色と深度のフォーマット（透明背景で PNG を出すならアルファ付きフォーマットをここで選ぶ）
- MSAA のサンプル数
- 画面表示の vsync（提示方法）

Tier2（設定として保持せず、毎フレームの描画呼び出しに渡すデータ。いつでも変更可）。

- レンダーツリーの中身（どのモデル・グリッド・向き表示を置くか）
- カメラの状態（CameraState。視野角は 45 度固定、ニア／ファーは自動）
- 背景のクリア色（RGBA。透明にするには Tier1 のアルファ付きフォーマットが前提）
- パーツの変形（NodeOverride）と色の上書き（ColorOverride）
- 時間・デルタ（`ITimeSource` 経由）

MSAA のサンプル数を変えるとフレームバッファとパイプラインの作り直しが必要なので Tier1 とし、
途中で変えたいときは「ターゲットを作り直す」明示的な操作で行う（こっそり再構築する「軽そうな
プロパティ」は作らず、コストを API 上で見えるようにする）。背景のクリア色は毎フレーム自由に
変えられる Tier2 で、透明にする前提条件としてのアルファ付きフォーマットだけが Tier1 である。

日々のコードは次のようになる。起動時に作成オプションでターゲットを 1 回作る。ループ中は毎
フレームの `Render(...)` だけを呼び、カメラ・ツリー・背景クリア色などの Tier2 を渡す。リサイズは
ライブラリがウィンドウを持つので内部で自動的に作り直す。MSAA・フォーマットの変更（まれ）は
明示的な「作り直し」を呼び、リサイズで必要になる作り直し経路と同じ 1 本に乗せる（新たな仕組みを
増やさない）。

クラス設計の含意として、Tier1 は変更不可の作成オプション（不変のレコード）に集約して生成時に
一度だけ渡し、Tier2 はエンジンの設定として保持せず毎フレームの入力として渡す。この線引きを
先に決めておけば、後で要件が変わってもクラス構造を壊さずに済む（作り直し経路に乗せるだけ）。
