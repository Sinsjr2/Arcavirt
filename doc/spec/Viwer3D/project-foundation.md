# プロジェクト基盤

本書は、本ライブラリが何を作ろうとしているか、なぜその技術を選んだか、どのように依存を
構成するかを定める。座標系・単位の正典は [index.md の座標系と単位](index.md#座標系と単位) に
ある。

## 概要と技術選定

### 目的と背景

本ライブラリの目的は、Blender で作られた glTF データを読み込み、画面に描画し、マウス・
キーボードで「機械パーツを様々な角度から観察・検査する」ことである。読み込んだモデルには
ローラーやギアが含まれ、各パーツには名前が付いており、特定のパーツを C# 側から回転・移動
できる。

単に画面に表示するだけでなく、Linux サーバー環境での画面なし（ヘッドレス）高速動作と、
OSS として配布しやすいクリーンな MIT ライセンスを満たす必要がある。これらの制約から、
Windows に依存する Direct3D や特定 UI に依存する仕組みは避け、既存のゲームエンジン（Unity や
Unreal Engine など）を使わず、低レイヤーのグラフィックス技術を組み合わせてゼロから自作する
道を選んだ。

### 技術選定

技術選定は次のとおり。Linux ヘッドレスで最も性能を発揮し、移植性を保てる構成を軸に据える。

- モデル読み込みは業界標準の glTF 2.0 を採用し、ライブラリは SharpGLTF を用いる。
- 描画基盤は NeoVeldrid を採用する。当初は .NET で実績のある抽象化ライブラリ Veldrid を
  使おうとしたが、本家 Veldrid は 2023 年 2 月以降保守が止まっているため、保守フォークの
  NeoVeldrid を採用する。NeoVeldrid はネイティブバインディングを Silk.NET に置き換えた
  フォークで、公開 API は維持されており、MIT ライセンス、ターゲットは net10.0 である。
  これに伴い、本プロジェクトのターゲットフレームワークは net10.0 以降とする。
- 名前空間・型は `Veldrid` ではなく `NeoVeldrid` を用いる（`NeoVeldrid.Key` など。型・
  メソッド・enum の名前はフォーク前と同一）。外部型の完全修飾の規約は
  [coding-conventions.md](coding-conventions.md#外部型の参照規約) に従う。
- グラフィックス API は Vulkan を主軸に据える。Vulkan は Linux で性能を発揮し、ヘッドレス
  処理にも強い。macOS には Metal バックエンドが存在しないが、NeoVeldrid は MoltenVK を
  同梱しており、追加設定なしに Vulkan を Metal 上で動かす。したがって macOS でも Vulkan を
  用いる。Vulkan 主軸は単なる選好ではなく、3 プラットフォームを 1 経路で賄う前提である。
- ウィンドウ制御はマルチプラットフォーム対応の SDL（Silk.NET.SDL）を用いる。内部設計と
  しては「画面表示（ウィンドウ）」と「メモリ上への描画（オフスクリーン）」のターゲットを
  完全に分離する。
- シェーダのクロスプラットフォーム対応は NeoVeldrid.SPIRV を用いる。コードとしては Vulkan
  用の GLSL を 1 種類だけ記述し、実行時に各バックエンドの言語へクロスコンパイルさせる。
  この SPIRV 変換はフォークで純 C# 実装になっており、ネイティブ C++ シムを持たない。これは
  ネイティブ依存を減らすクリーンな依存方針に好都合である。
- 時間管理は 3D ループに特化した独自のシンプルな `ITimeSource` インターフェースを定義する。
  「現実の時間通りに動くリアルタイム用」と「実際の時間を無視して GPU の限界速度で時間を
  進めるステップ用」の 2 実装を切り替えられるようにする。.NET の `TimeProvider` は
  システム時刻や非同期タイマー向けであり、3D 描画で必要な「前フレームからの経過時間
  （デルタタイム）」や「時間の進み方の操作（ポーズやスロー）」にはオーバースペックで
  複雑になるため採らない。

### メディア出力のスコープ

メディア出力は、PNG 静止画の保存と、生ピクセルデータのリアルタイム提供 API に特化する。
動画への保存は実装しない。

C# の純粋なコードだけで動画（H.264 など）の圧縮を行うとパフォーマンスが極端に悪化するうえ、
動画圧縮技術には巨額の特許ライセンス（特許訴訟リスク）が絡む。外部ツール（FFmpeg など）を
使わずに 100% C# 完結かつ MIT ライセンスを維持するのは極めて困難である。そこで動画機能を
バッサリ削る（スコープダウン）ことで、外部依存のない 100% ピュア C# での静止画保存と生
ピクセル提供に焦点を絞った。

なお、描画完了後にピクセルデータを引き抜く具体的な機構（解像・ステージング・非同期取り出し）
は描画の流れと一体のため、[render-engine.md の画像キャプチャ機構](render-engine.md#画像キャプチャ機構)
に置く。

## アーキテクチャと依存

### プロジェクトの物理分割

将来のユーザーの利便性と拡張性を最優先し、最初からプロジェクト（.csproj）を物理的に 3 つへ
分割する。

- Core … 画面なしの心臓部。
- Platforms.SDL2 … 画面表示用。
- MediaOutput … 出力用。

1 つにまとめると開発は楽だが、Linux サーバーで「画面なし機能だけ」を使いたいユーザーにも、
画面表示用の余計なライブラリが強制インストールされてしまう。分割により、必要な部分だけを
依存に取り込める。

### 形式に依存しない境界

描画エンジン（描画・上書き・カメラ・キャッシュ）は、glTF や SharpGLTF を一切知らず、形式に
依存しない境界インターフェース `IDrawableSource` だけに依存する。glTF 読み込みはその 1 実装で
あり、内部で SharpGLTF を使う。

これにより、SharpGLTF は読み込み部品の中だけに閉じ込められ、描画エンジン本体は SharpGLTF に
依存しない。別形式（OBJ・FBX 等）を足したくなったら、同じ `IDrawableSource` を実装する部品を
1 つ書くだけでよく、描画エンジン・既存ノードは変更不要である。名前や階層を持たない形式
（STL など）は、上書き対象が存在しないので「静止表示だけ」に自然に縮む。今は glTF の 1 実装
のみを作り、他形式は作らない。

`IDrawableSource` の正典（契約の定義と、宣言ツリーから描画命令への接続）は
[render-engine.md の宣言ツリーと描画](render-engine.md#宣言ツリーと描画) に置く。本書では
「描画エンジンはこの境界だけに依存する」という依存方針のみを定める。

### UI とネイティブ依存の方針

ImGui は一切使わない。ImGui は C++ 実装で、.NET から使うには各 OS 向けのネイティブブリッジを
伴う。これを避け、UI まわりを追加のネイティブ依存なしの純 C# に保つことで、移植性・保守性・
ビルド容易性を高める。なお、その下の GPU（Vulkan）・ウィンドウ（SDL）は Silk.NET 経由で
ネイティブを叩くが、これは描画・ウィンドウ表示に不可避な土台であり消せない。ImGui を外して
得られるのは「避けられるネイティブ依存を 1 つ無くす」ことである。

画面に表示するのは 3D モデルと向き表示（ナビゲーションギズモ）だけで、一般のボタン類は
作らない。視点操作・パーツ制御などは、マウス・キーボード・テキストコマンドをアプリ側が
ライブラリの API に結びつけて行う。

### シングルトン不使用

グローバルな静的状態（シングルトン）は一切使用しない。すべての状態やデバッグ機能は、
明示的に生成したエンジン／コンテキストのインスタンスを経由して提供する。テスト可能性
（テスタビリティ）や、ヘッドレス・並列処理での安全性を保証するためである。

```csharp
// シングルトンではなく、インスタンスを明示的に生成
var renderEngine = new CoreRenderEngine(graphicsDevice);

// デバッグ用 API もインスタンス経由で安全に取得
string[] validPaths = renderEngine.Assets.GetAvailableNodes("machine.gltf");
```

### ステートレス宣言の原則

状態は 100% アプリケーション側が保持し、ライブラリは渡された宣言をその通り描く（単方向
データフロー）。状態の不整合が起きないこの構造の詳細（毎フレーム再構築・差分なし）は
[scene-nodes.md の宣言的シーン記述の仕組み](scene-nodes.md#宣言的シーン記述の仕組み) に置く。
