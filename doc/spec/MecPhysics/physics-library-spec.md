# 物理シミュレーションライブラリ 確定仕様

bepuphysics2 上に構築する C# 物理シミュレーションライブラリの設計確定書。
別途設計済みの「ステートレス 3D 表示ライブラリ」(`index.md`)と連携し、
生産機・折り機／糊付け機の紙搬送機構(ギア・モーター・ローラー・センサー・変形シート)を模擬する。

---

## 0. 設計の指針(全体を貫く原則)

- **標準 bepu の範囲で作る。** 物理エンジン内部に独自機構を作り込まない(デバッグ困難を避ける)。標準の拡張点(複合形状・拘束・narrow-phase コールバック・スリープ等)は使うが、内部改造はしない。
- **完全に単一スレッド。** 表示ライブラリと揃える。
- **一方向データフロー。** アプリが 物理を step → 姿勢を読む → 宣言的レンダーツリーを組む → 描画。物理はシーングラフの一部ではなく、独立した姉妹システム。
- **オーサリングの役割分担(後述)を厳守。** glTF＝幾何、JSON＝構造・数値、C# コード＝実行時の制御ロジック。

---

## 1. アーキテクチャ

- 物理ライブラリは**内部的にステートフル**で、bepu の `Simulation` を所有する。表示ライブラリは**ステートレスのまま**で、姿勢だけを消費する。
- **物理→レンダラのデータ契約**：レンダーノードごとに `{ 識別子, Pose = position(Vector3) + orientation(Quaternion) }`。同一性キーは **glTF ノード名**(フォールバックの正典キーはノード index)。
- 物理は描画と分離された姉妹システム。アプリの 1 フレームは「物理 step → 姿勢取得 → 宣言的に描画ツリー構築 → 描画」。

---

## 2. 座標・単位・軸規約

- 座標は `index.md` を継承：**Y-up 右手系、1 単位 = 1 m**。bepu も一致するため**変換不要**。
- **軸規約：ノードのローカル +Z を主軸とする。** 回転軸・ヒンジ・ギア軸・センサー光線の方向は、すべて当該ノードのローカル +Z。ノード原点 = ピボット／光線始点。
  - 理由：Blender の円柱は既定でローカル Z 方向に長い。ローラー／ギアの衝突円柱の対称軸 = 回転軸 となり、自然に一致する。

---

## 3. オーサリングの分担

**原則**：空間・幾何で視覚的オーサリングが要るもの → glTF。論理・スカラ値でコードで書けるもの → JSON。実行時の制御判断 → C# コード。
**鋭い言い方**：単項で自己位置を持つ実体 → glTF ノード。関係(2 項以上)を持つ構造 → JSON(ノード名で参照)。

| 置き場 | 内容 |
|---|---|
| **glTF** | 衝突形状の種類＋寸法、配置(transform)、センサー光線、スポーン点、シンク／排出領域、糊ノズルのノード、シートの**粗い制御メッシュ**(折り／スコア辺のタグ付き) |
| **JSON** | body の種別＋質量、拘束(ギア)、アクチュエータ、全体物理パラメータ(dt・サブステップ・反復・重力・スリープ)、シート分割レベル・サイズ、材料(摩擦等)、媒体パラメータ、スコアクラス定義 |
| **C# コード** | 実行時の制御ロジック(センサー読取→判断→アクチュエータ指令→step の閉ループ) |

- 拘束・関係が JSON にあるのは、**glTF は木構造だが拘束はグラフの辺**だから。glTF には一級の辺が無い(三角形＋頂点属性のみ)。これが、折り／スコアを**制御メッシュ上のタグ**として持たせ、ライブラリ側で細分時に**タグを継承**する設計の理由でもある。
- 妥当性は React + Babylon.js(Havok V2 / `Physics6DoFConstraint` / `addConstraint`)でも確認済み——あちらでも拘束は名前／参照での結線になる。

## 4. ボディ

- 種別：**static / kinematic / dynamic**。
- **規則**：衝突形状プロパティを持つ glTF ノードは physics body であり、既定は **static**。JSON の `bodies` テーブルは **kinematic / dynamic のみ**を列挙して種別を上書きし、質量を与える(JSON 最小化)。
- **複合(Compound)ボディ**：1 body = 1 つ以上の glTF ノード形状を剛体結合(bepu `Compound`)。
  - JSON エントリ：`{ id, members[ノード名…], class, mass }`。拘束・アクチュエータは body id を参照。
  - 出力時は**メンバーノードごとの姿勢に展開**(bodyPose ∘ memberLocalOffset)するので、レンダラ契約は不変。
- dynamic は質量必須(慣性は 形状＋質量 から算出)。kinematic / static は質量を無視。

## 5. 機構(ギア・アクチュエータ・ローラー)

### ギア
- bepu 標準 **`AngularAxisGearMotor`**(`VelocityScale` = 比)。位相ロックではなく**速度結合**(許容)。

### アクチュエータ
- **kinematic 軸**を、**位置指令 or 速度指令**で駆動(トルク指令は廃止)。
- 実装は毎 step 角速度を設定(位置モードは目標へ向かう速度を算出。姿勢を瞬間移動させない)。
- **無限権限**(ストール・逆駆動なし)——「step を取りこぼさない」の帰結として許容。
- モーター目標は実行時のアプリ状態。

### モーター忠実度
- **step 取りこぼし／ストールなし、電磁モデルなし。** ステッピングは kinematic な指令角として扱う(パルス = 整数累積で厳密)。dt を kHz の電気レートに合わせる必要はない。

### ローラー(搬送)
- **本物の摩擦接触**(把持拘束モデルは検討後に却下)。搬送は 摩擦 = μ × 垂直抗力 から**創発**する。
- 駆動ローラーは kinematic(モーター／ギア駆動)。**スリップは接触点で創発**(ローラーが止まるのではない)。
- ニップの挟み込み垂直抗力は **バネ付きアイドラ**から：自由回転する dynamic ローラーをバネで押し付ける(プリロードは JSON)。
- シート↔ローラーは**接触ペア**。

---

## 6. シート／媒体(最重量サブシステム)

紙は変形体だが bepu は剛体エンジンなので離散化する。

- **シート = 薄い剛体タイルの 2D 格子**(1D 鎖は、折りが MD/CD 両方向に起きるため却下)。
- タイルは共有辺で**辺全体のレボリュート結合**で繋ぐ。結合に**弾塑性の曲げバネ**を持たせる。面内非伸張は 辺全体レボリュート から自動。
- **塑性(折り癖)**：標準の bepu 角度拘束(静止角まわりの弾性バネ)＋ アプリ側で毎 step、降伏閾値を超えたら**静止角を更新**(= 塑性)。標準 API の使い方であり、bepu 内部改造ではない。降伏後は**どこでも塑性**(ジャムの座屈も癖が付く)。
- **スコア線(折り／罫)**：制御メッシュの該当辺に**クラス名でタグ付け**(1 シートに複数スコアクラス可)。JSON が各クラスの弱化 `{ 曲げ剛性係数, 降伏角 }` を定義。**対称**(折り方向は持たない。方向は機械のプラウから創発)。調整は「公称の降伏角を高く、スコアの降伏角を低く」。
- **自己衝突**：辺を共有する隣接タイルは自動除外。**非隣接タイルは自己衝突する**(折った半身が重なるため)。**シート↔シート衝突 ON**(ジャム)。
- **スポーン**：glTF のスポーン点ノード＋実行時テキスト指令で媒体／テンプレートを選び(サイズは JSON、上書き可)生成。
- **非一様分割**：Blender は**粗い制御メッシュ**を作る(折り／スコア辺が識別・タグ可能)。JSON が分割**レベル**を与え、ライブラリが**単純(線形／中点)細分**(Catmull-Clark ではない)を**決定的タグ継承**付きで実行。テンプレートを拡大縮小しても**トポロジ保存 → タイル数(コスト)はサイズと独立**。スコア／折り位置はメッシュに比例。
- **材料パラメータ(JSON、媒体／テンプレートごと)**：坪量 g/m²(→タイル質量)、厚み mm(= 視覚 = 衝突厚。実際の紙厚を使い、視覚／衝突の分離はしない)、曲げ剛性(→内部で bepu バネの周波数／減衰)、降伏角、微小減衰。ヒンジごとの剛性／降伏は分割レベルで自動スケールし、**解像度非依存**。
- **描画**：シート = 実行時生成の手続き的タイル四角ノード。各々が body で、姿勢を渡す(レンダラは box/cylinder/capsule/sphere＋メッシュの手続き的プリミティブを受け付ける)。

## 7. 接触・タイムステップ・トンネリング

### 衝突フィルタ
- **ユーザー定義の衝突グループは持たない。**
- 規則：**衝突形状を持つ body だけが参加**。本当に干渉する部品(ローラー・ガイド／バッフル・シート)にだけ形状を与える。機構のみの部品(ギア)には形状を与えず、拘束で結合。
- エンジンが自動除外：拘束ペア、複合メンバー、シート内隣接。形状を持つ body 同士は「全部ぶつかる」が正しい。

### 材料・摩擦
- **body ごとのみ**(ペア別上書きは廃止)。各 body／媒体は摩擦＋反発(反発 ≈ 0、紙は跳ねない)を持ち、接触 μ は両者の固定内部ブレンド。
- bepu の摩擦は単一係数クーロン(静／動の区別なし)——許容。
- 対応：bepu `AllowContactGeneration`(フィルタ)＋ `ConfigureContactManifold`(摩擦)。

### タイムステップ
- **固定 dt ＋アキュムレータ**、描画から**分離**(より速く／多く回せる)、**サブステッピング**(bepu の勘所：サブステップ＋速度反復 ≈ 1)、全て JSON 設定。
- **単一機内の決定性のみ**(クロスプラットフォームのビット決定性は対象外)。リアルタイム不要(計算でき次第進む)。

### トンネリング(薄く速いシート)
- 実厚を維持。主防御は **bepu の投機マージン**を 1 step の移動量 v·dt に合わせる(検出距離であり、形状を膨らませない・浮かせない)＋ 速度膨張ブロードフェーズ。最速 body には CCD を任意適用。dt 下限 ≈ 厚み/速度(例：0.3 mm @1 m/s → dt < ~0.3 ms ≈ 3 kHz)。
- 重力 ON ＋坪量質量(静止摩擦・たわみ・沈降に必要)。極軽タイルはサブステップ／減衰を増やす。

### コスト感(単一スレッド)
- 支配項は機械でなく**シート**。折られた 1 枚 ≈ 3T 項目(T=タイル、≈2T 曲げヒンジ＋≈T 自己接触)。拘束ソルブ ≈ 0.1–0.3 µs/件(bepu の布ベンチ:16384 球＋64470 拘束で 8 スレッド ≈9.5 ms/frame、を錨に)。
- 複数枚の 2D 自己接触折りは**明確にオフライン**(リアルタイム未満)。タイルを半分にすると 4 倍(二次)。静止シートはスリープ(≈0)。**目標 CPU で校正用マイクロベンチを推奨。**

## 8. センサー

- **レイキャスト**。glTF に配置(始点 = ノード、方向 = ローカル +Z、距離は JSON)。
- **離散的な step 後サンプリング**(解析的なサブ step エッジ検出は廃止)。状態は各 step 後に読み、エッジは連続読取の比較で導出(dt 粒度)。
- 注意：dt は、速く薄い特徴が 1 step 内に光線へ入って出ない程度に小さく(トンネリング対策で既に kHz dt なので問題なし)。
- **制御ループはアプリ側**(物理内にコントローラを持たない)。動作は次の step 境界で反映。

---

## 9. 糊付け(折り機／糊付け機)

### 適用
- いまは**機械が塗布**のみ(Blender 事前塗布は将来拡張として同じデータ構造で予約)。
- 糊ノズル = glTF ノード、アプリが ON/OFF。ON のとき**ローカル +Z にレイを撃ち**、当たった body の当たり点に糊を置く(シートでも一般物体でも)。硬化／オープンタイムは現状不要。

### 表現(普遍形 — 全オブジェクト対応)
- **糊マーク = `{ 付着 body, ローカル点, ローカル法線(糊面の向き), 半径／量 }`。** bepu のエンティティではない。
- タイルも一般物体も同一表現(タイル面の糊は「面上の点＋面法線」という退化ケース)。

### 接合検出(アプリ側相関 — 軽量・bepu 不変)
- bepu の**標準接触コールバック**(摩擦で既に使用)が body 対の接触＋接触点を報告。
- アプリが「その body 上に、接触点の近くで、**糊面が相手側を向いた**マークがあるか」を判定。
- 該当すれば step 後に**標準 Weld** を生成。
- **面の向き判定**はレイの当たり法線から無料で得られ、糊が付いた裏面がローラー等に触れても誤接合しないために必要(糊の方向選好ではなく「糊がどちらの面にあるか」の事実)。
- 計算量：bepu が既に計算した接触に対する **O(k)**(その body のマーク数、k は小)。衝突判定のやり直しではない。糊を bepu 子形状にする案は、narrow-phase 増・実行時形状再構築・幾何の乱れを最重量部に上乗せするため却下。

### 接合
- 接触で**即時・剛(標準 Weld)**。**Weld は body 対ごとに 1 本**(糊の筋がタイルを N 枚跨いでも Weld は N 本=タイル対ごと。マーク数では頭打ちしない)。

### パターン(曲線・ドット)
- 点マークの集合で表現。ノズルの **ON 連続 → 線・曲線**、**ON/OFF パルス → ドット**(パターン = ON/OFF タイミング × 運動)。Weld 粒度はタイル対なので**機能精度は落ちない**。見た目だけ細かくしたければ、描画用にレイ当たり点を別途記録(接合とは分離)。

## 10. ライフサイクル

- **spawn**(済)→ **稼働**(静止で **bepu スリープ** = コストほぼ 0 のまま残置)→ **除去**。
- 除去は **glTF のシンク領域ノード**(排出口・リジェクト口。スポーン点の逆)に完全に入ったらアプリが実施。加えて**明示の除去コマンド**(手動掃除・リセット)。
- **除去単位は「weld で繋がった連結塊」**(完成した箱)。シートだけ消すと weld が宙に浮くため、塊の body(タイル)・ヒンジ・weld・糊マークを一括で片付ける。

## 11. 制御インターフェース

- 提供は**基盤(C# API)のみ**。宣言的な制御 DSL は将来拡張。
- **基盤 = C# 制御 API**：id 付きハンドルをアプリが毎 step 叩く。閉ループ(センサー読→判断→指令)はアプリの C# に書く。
- **手動 = 組み込みのコンソール＋キーボード**(検証用。id で軸選択、キーで正逆、ノズル ON/OFF)。
- **プロファイル = アプリのコード**(台形速度などのヘルパは任意)。

### 値アクセスの統一インターフェース(専用名前空間)
- **`ISensor<T> { T Read(); }`** — 読み取り専用。**機械の動きを読むものは全てセンサー**。
- **`IOutputTransducer<T> { void Write(T value); }`** — 書き込み専用。**光出力・熱出力・アクチュエータ等の物理出力を生むもの = 出力変換器**。
- **メソッドで定義**(プロパティでない。インターフェース実装を考慮)。**読み／書きを分離**し、**対応するものだけ実装**(使えないメソッドが見えて誤解する事態を構造で防ぐ)。**ジェネリック**で bool/float を同形に扱う。
- 対応：センサー状態 = `ISensor<bool>`、センサー距離 = `ISensor<float>`、ノズル／モーター有効 = `IOutputTransducer<bool>`、モーター速度・位置／ヒーター = `IOutputTransducer<float>`。
- **bind／コールバックなし。** 毎 step アプリが Read/Write する。
- **論理計算はライブラリ外**(対象外)。AND/OR/ラッチ等の組み合わせはアプリの素の C# で(`nozzle.Write(s1.Read() && s2.Read())`)。
- **エッジもライブラリ外。** センサーは bool 状態を返すだけ。立ち上がり等はアプリが前 step の Read と比較して導出。

## 12. ローダ(読み込み・検証・単位)

### 単位
- **項目ごとに人に優しい単位を明示**(厚み = mm、坪量 = g/m²、角度 = 度 など)し、ローダが**内部 SI(m・rad・kg)に変換**。座標・幾何は **glTF の m(1 単位 = 1 m)を正典**。

### エラー方針(例外を投げない・まとめて返す)
- ローダは**結果オブジェクトを返す**：`LoadResult { bool Success; IReadOnlyList<Diagnostic> Diagnostics; World? World }`。`Diagnostic { Severity(error/warning), Location(ファイル・ノード／id・項目), Message }`。
- **一回の走査で全チェックを回し診断を貯めてから返す**(最初のエラーで止めない)。error が一つでも → `Success=false`・World なし、ただし**見つかった全 error を列挙**(まとめて直せる)。
- **I/O・parse 失敗も Diagnostics に入れる**(例外にしない)。呼び出し側は「`Success` を見て `Diagnostics` を読む」一本道。例外は本物のプログラマ誤用バグのみに限定。
- 各診断は単体で意味を持つ粒度に。純粋な連鎖は根を優先。

### 検証項目
- 参照ノード名の解決(拘束・アクチュエータ・bodies・センサー・シンクの参照)。
- body 種別の整合(アクチュエータ対象 = kinematic、ギア従動 = dynamic、dynamic = 質量あり)。
- 必要な所に形状があるか。
- 参照したスコア／材料／媒体クラスが定義済みか。
- id 重複。値の範囲(質量・厚み等は正)。

## 13. bepu API 対応(使用する標準機能)

- ギア：`AngularAxisGearMotor`(`VelocityScale`)/ `AngularAxisMotor`
- 接合：`Weld`
- シートのヒンジ：レボリュート／角度サーボ拘束＋バネ(frequency / damping)
- 複合：`Compound`(接触の child index)
- タイムステップ：`SubsteppingTimestepper` / `SolveDescription`(サブステップ＋低速度反復、StabilityTips)
- 連続検出：投機接触＋ `ContinuousDetection`(CCD)
- レイ／スイープ：`Simulation.RayCast` / `Sweep`(`IRayHitHandler` / `ISweepHitHandler`)
- narrow-phase コールバック：`INarrowPhaseCallbacks` の `AllowContactGeneration`＋`ConfigureContactManifold`(`PairMaterialProperties` 摩擦)
- 単一スレッド = 決定的。スリープ状態(静止 body は安価)。
- Blender → glTF：カスタムプロパティを `node.extras` にエクスポート(モディファイア適用後メッシュ)。`KHR_physics_rigid_bodies` は非標準で SharpGLTF が解釈せず・拘束空間の互換問題があるため不採用。

## 14. 明示的な割り切りと将来拡張

### 割り切り(合意済み)
- ギアは速度結合(位相ロックなし)。アクチュエータは無限権限(ストール／逆駆動なし)。
- 摩擦は単一係数クーロン(静止摩擦の別扱いなし)。
- 決定性は単一機内のみ(ビット再現なし)。リアルタイム保証なし(複数枚折りはオフライン)。
- センサーは dt 粒度の離散検出。

### 将来拡張(同じデータ構造で予約)
- Blender 事前塗布の糊。
- 宣言的な制御 DSL(「センサー X 立ち上がりでモーター Y を速度 Z」式)。
- `Signal<T>` 的に float の組み合わせまで広げる場合の補助(現状は読み書きのみ)。
- 糊の硬化／オープンタイム。
